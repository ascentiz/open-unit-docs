# 安全模型

Open Unit 平台旨在支持实验，同时不削弱底层设备的安全保障。

## 安全原则

1. 设备从不允许发送动作命令的状态启动。
2. 命令权限必须明确请求，并且可以明确撤销。
3. 硬性限制由 Exoskeleton Unit 执行，而不只依赖应用约定。
4. 故障处理是正常集成流程的一部分，不是罕见的边界情况。

## 会话状态模型

最小会话生命周期应类似于以下模型：

| 状态 | 含义 |
| --- | --- |
| `idle` | 设备可用，但没有活动客户端会话 |
| `unarmed` | 客户端会话已建立，但会产生运动的命令被阻止 |
| `armed` | 客户端可在已批准的边界内发送命令 |
| `fault` | 设备检测到需要干预或复位的情况 |
| `estop` | 立即停止状态，需要明确的恢复流程 |

具体名称可能演进，但状态转换应始终明确。

## 预期保护机制

平台应提供：

- 命令会话的心跳或租约到期机制
- 受边界约束的模式切换
- 对操作人员可见的故障码
- 可审计的会话开启、使能、解除使能及故障事件日志

## 开发者指南

运行在 Open Unit 上的应用应：

- 将 `armed` 视为需要获取的权限，而非默认状态
- 在每个控制序列之前验证状态
- 在日志及操作界面中显示被拒绝的命令
- 当遥测或会话的新鲜度无法确认时，默认禁止命令执行

## 不属于 Open Unit 应用的职责

以下安全保障不应仅由应用实现：

- 最终关节限制执行
- 过流关断
- 急停处理
- 对时序敏感的电机安全行为

这些控制属于 Exoskeleton Unit 一侧的职责。
